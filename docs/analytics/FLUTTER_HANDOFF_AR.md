# تسليم مهام تتبع التطبيق — Flutter

هذا الملف جاهز لإرساله لمبرمج تطبيق Clean Station. مسؤولية التنفيذ داخل Flutter تقع على مبرمج الموبايل. إعدادات Firebase/GA4 وBranch ومفاتيحها موجودة ومربوطة مسبقًا حسب تأكيد مالك المشروع؛ لا يحتاج المبرمج مفاتيح جديدة لهذا العمل.

## المطلوب من مبرمج التطبيق

1. مراجعة أحداث التطبيق الحالية ومقارنتها بالقائمة أدناه؛ لا يعيد إضافة حدث موجود أو يرسل الاسم نفسه مرتين.
2. تنفيذ أحداث رحلة التصفح والشراء التي مصدرها واجهة التطبيق فقط:
   - `view_item_list`
   - `add_to_cart`
   - `remove_from_cart`
   - `view_cart`
   - `begin_checkout`
   - `checkout_blocked`
   - `add_payment_info`
3. منع التطبيق من إرسال أحداث ما بعد إنشاء الطلب التي يصدرها الباك إند، مثل حالات الطلب، الدفع المؤكد، `purchase`، المحفظة والولاء. الباك إند هو مصدر الحقيقة لهذه الأحداث.
4. إرفاق `analytics_context` مع طلب إنشاء الطلب، وإرفاقه عند شحن المحفظة إن كان مسار الشحن يرسله من التطبيق:

```json
{
  "analytics_context": {
    "app_instance_id": "Firebase App Instance ID",
    "app_version": "1.2.3+45",
    "session_id": 123456789,
    "platform": "android",
    "branch_first": {
      "channel": "optional",
      "feature": "optional",
      "campaign": "optional",
      "click_id": "optional",
      "clicked_branch_link": true,
      "click_timestamp": 1790000000
    },
    "branch_latest": {
      "channel": "optional",
      "feature": "optional",
      "campaign": "optional",
      "click_id": "optional",
      "clicked_branch_link": true,
      "click_timestamp": 1790000000
    }
  }
}
```

كل السياق اختياري ومتوافق مع الخادم الحالي. `platform` يقبل `ios` أو `android`؛ `app_version` نص حتى 100 حرف؛ `session_id` رقم صحيح غير سالب. بيانات Branch داخل `branch_first` و`branch_latest` اختيارية. لا ترسل اسم العميل أو هاتفه أو بريده أو عنوانه أو قيم الدفع المحسوبة ضمن سياق التحليلات.

5. استخدم `app_instance_id` الصادر من Firebase، واحتفظ بأول إسناد Branch وآخر إسناد وفق بيانات SDK؛ لا تخترع attribution ولا تستبدل القيمة الأولى عند تغير الحملة.
6. نفّذ إصدار التطبيق بطريقة تسمح بوجود الإصدارات القديمة والجديدة معًا: لا تغيّر API إلى حقول إلزامية، ولا ترفع الحد الأدنى للإصدار ضمن هذا العمل. أرسل `app_version` في كل طلب جديد وشحن محفظة، مع استمرار عمل الطلب إذا غاب الحقل.
7. اختبر iOS وAndroid على Staging: طلب قديم بلا سياق، طلب جديد بسياق كامل، طلب بسياق جزئي، مسار شحن المحفظة، وأحداث الواجهة مرة واحدة لكل تفاعل. لا تختبر بدفعات مالية حقيقية.
8. سلّم أرقام وإصدارات البناء، نتائج الاختبار، وأي أسماء أحداث قديمة وجدت في التقارير حتى يمكن مواءمتها مع `schema_version=2`.

## ما يحتاجه المبرمج من صاحب المشروع

- تكليفه ومشاركة مستودع Flutter/صلاحيات العمل المعتادة.
- إرسال هذا الملف وخطة التتبع المعتمدة.
- التنسيق لإتاحة بيئة Staging وبيانات اختبار إذا لم تكن متاحة للمبرمج.

لا يلزم من صاحب المشروع تجهيز مفاتيح Firebase/Branch/GA4 أو اتخاذ قرار جديد للأحداث؛ مالك المشروع أكد أن الربط والمفاتيح الصحيحة مجهزة مسبقًا. لا يوجد رفع إجباري للحد الأدنى للإصدار. يبقى قرار موعد مراجعة الانتقال (90% من النشطين أو 4–6 أسابيع) لدى المنتج عند بدء إطلاق النسخة.
