# خطة تطوير نظام الإشعارات ولوحة التحكم في Clean Station

**الحالة:** مقترحة للاعتماد قبل التنفيذ  
**الإصدار:** 1.2 — محدث بعد المطابقة مع كود CleanStation الفعلي  
**النطاق الحالي:** Laravel ولوحة التحكم وتهيئة عقود API فقط  
**خارج النطاق الحالي:** تعديل تطبيق Flutter؛ تُجهز له خطة مستقلة بعد اعتماد هذه الخطة  
**التاريخ:** 2026-09-26

## 1. الهدف

تطوير نظام الإشعارات الحالي بحيث يستطيع Clean Station معرفة الجمهور المستهدف، والأجهزة القابلة للإرسال، وحالة كل توكن، وحالة سماح المستخدم، وآخر نشاط معروف، ونتائج الحملات بصورة صحيحة؛ مع المحافظة على الجداول والمسارات الحالية وتطويرها تدريجياً دون إعادة بناء النظام من الصفر أو تعطيل التطبيق المنشور.

الهدف ليس رفع رقم الإرسال شكلياً، بل جعل الأرقام قابلة للتفسير واتخاذ القرار، ثم تمكين تطبيق Flutter من مزامنة الجهاز والتوكن والصلاحية والنشاط مع Laravel في المرحلة التالية.

## 2. خط الأساس المثبت من Production

### 2.1 الحملة المرجعية

الحملة رقم `1120558` أعطت النتائج التالية:

| المؤشر | العدد | المعنى الصحيح |
|---|---:|---|
| المستخدمون المستهدفون | 14,105 | جميع المستخدمين غير المحذوفين وقت تنفيذ الحملة |
| الحالة `sent` | 2,142 | توكنات قُبلت في اشتراك FCM Topic؛ ليست دليلاً على التسليم |
| الحالة `failed` | 11,963 | جميعها بسبب `No device token` |
| أخطاء FCM أخرى | 0 | لا توجد أخطاء أخرى مسجلة لهذه الحملة |
| نسبة وجود التوكن | 15.19% | نسبة المستخدمين الذين كان للنظام توكن مرتبط بهم |
| نسبة عدم وجود توكن | 84.81% | لا تعني أن العملاء وهميون أو حذفوا التطبيق |

### 2.2 الأجهزة

| المنصة | التوكنات المسجلة |
|---|---:|
| iOS | 1,990 |
| Android | 155 |
| الإجمالي | 2,145 |

يوجد ثلاثة مستخدمين لديهم أكثر من جهاز، بينما المسار الحالي يختار توكناً واحداً فقط لكل مستخدم. لذلك ظهر 2,142 مستخدماً مقابل 2,145 جهازاً.

### 2.3 إعداد السماح الحالي

| `is_allow_notify` | إجمالي المستخدمين | لديهم توكن |
|---|---:|---:|
| `0` | 7,722 | 1,885 |
| `1` | 6,439 | 257 |

الحملة المرجعية أرسلت إلى جميع أصحاب التوكنات دون مراعاة `is_allow_notify`، بما في ذلك 1,885 مستخدماً قيمتهم `0`. وفي المقابل يوجد 6,164 مستخدماً قيمتهم `1` ولا يملكون توكناً. لذلك لا يجوز اعتبار هذا الحقل دليلاً على صلاحية إشعارات الجهاز.

### 2.4 موثوقية الـQueue

يوجد في Production:

- 11 وظيفة `SendNotificationJob` فشلت بسبب `TimeoutExceededException`.
- وظيفتان فشلتا لأن `explode()` استقبل Array بدلاً من String في `NotificationsManger.php:86`.

## 3. قرارات معمارية ملزمة

1. **لا تُحذف الجداول الحالية ولا يُعاد بناء النظام من الصفر.**
2. **يُمدد جدول `devices`** ليصبح المصدر الأساسي لحالة تثبيت التطبيق والتوكن والصلاحية والنشاط.
3. **يبقى جدول `notifications`** هو سجل الحملة أو الإشعار الرئيسي.
4. **يبقى جدول `users_notifications`** لربط الحملة بالمستخدم ولصندوق الإشعارات داخل التطبيق، ولا يُستخدم وحده كدليل على تسليم Push.
5. **يُمدد جدول `notification_tokens`** ليصبح سجل محاولة الإرسال لكل جهاز، بدلاً من إنشاء جدول موازٍ يؤدي الوظيفة نفسها.
6. **يبقى `is_allow_notify` مؤقتاً** للتوافق، لكنه يُعامل كتفضيل تسويقي داخل Clean Station وليس كصلاحية نظام التشغيل.
7. **صلاحية iOS أو Android تحفظ على مستوى الجهاز** في `devices.notification_permission`.
8. **تفصل الحملات التسويقية عن الإشعارات التشغيلية** مثل تحديثات الطلب والتوصيل.
9. **لا يُستخدم مصطلح تم التسليم** إلا عند وجود دليل تسليم حقيقي؛ قبول FCM يسمى `accepted_by_fcm`.
10. **كل تغيير يُنفذ بصورة إضافية ومتوافقة مع التطبيق الحالي** وتحت Feature Flags عند الحاجة.
11. **جدول `devices` أصل مشترك لتطبيقات العميل والسائق والفني**؛ لا تطبق عليه افتراضات تخص تطبيق العميل وحده.
12. **جدول `users_notifications` Polymorphic ومشترك مع البنرات**؛ شرط `notifications_type` إلزامي في جميع استعلامات الحملات.
13. **لا Unique Constraint جديد على التوكن أو installation في هذه المرحلة**؛ تدار الفردية منطقياً بسبب SoftDeletes ومسارات Logout القديمة.

### 3.1 قفل التوافق الخلفي مع نسخ التطبيق الحالية — Binding

هذه القواعد شرط نشر وليست توصيات. الهدف أن يستمر المستخدم الذي لا يحدّث تطبيقه في استخدام Clean Station بصورة طبيعية ودون ظهور أخطاء أو إجباره على التحديث.

1. **لا يعتمد أي تعديل Backend في هذه المرحلة على وجود إصدار Flutter جديد.** تعمل المنظومة الجديدة عند غياب الحقول والأحداث الجديدة، وتبقى النسخ القديمة على المسار Legacy الحالي.
2. **لا تتغير المسارات الحالية أو HTTP Methods أو أسماء الحقول الإلزامية أو شكل الاستجابة الذي يقرأه التطبيق الحالي.** يمكن إضافة حقول اختيارية فقط، ولا تُحذف أو يُعاد تسمية الحقول القديمة.
3. **كل أعمدة قاعدة البيانات الجديدة Nullable أو لها Default آمن.** لا توجد Migration تجعل بيانات جديدة مطلوبة من التطبيق القديم، ولا يوجد Drop أو Rename لعمود مستخدم حالياً.
4. **تبقى APIs الحالية فعالة.** تُضاف APIs الجديدة لمزامنة الجهاز والأحداث، لكن عدم استدعائها من التطبيق القديم لا يمنع تسجيل الدخول أو الطلب أو Inbox أو استقبال الإشعارات وفق المسار الحالي.
5. **يبقى تسجيل التوكن الحالي مدعوماً.** إذا لم يرسل التطبيق `installation_id` أو الصلاحية أو نسخة التطبيق، يحفظ السيرفر التوكن بالطريقة المتوافقة ويصنف الجهاز `legacy/unknown` بدلاً من رفض الطلب.
6. **لا تُطبق قواعد الحجب على القيم Unknown.** قبل انتشار نسخة Flutter الجديدة يبقى `permission_mode` و`marketing_preference_mode` في وضع `observe`، ولا يُمنع مستخدم قديم لأنه لم يرسل بيانات جديدة.
7. **لا يتغير Payload الذي تعتمد عليه النسخ الحالية.** تبقى مفاتيح FCM الحالية وأنواع قيمها موجودة، وتضاف أي مفاتيح جديدة بصورة اختيارية ومتوافقة. يمنع تغيير قيمة من String إلى Array أو Object في المفتاح نفسه.
8. **لا يوجد Forced Update ضمن هذه الخطة.** ولا تُرفع `minimum_supported_app_version` بسبب مشروع الإشعارات.
9. **يعمل الإرسال الجديد والقديم خلف Feature Flags مستقلة.** يمكن تعطيل المسار الجديد فوراً والعودة إلى المسار الحالي دون Rollback لقاعدة البيانات.
10. **لا تُحذف أجهزة أو توكنات Legacy أثناء الإطلاق.** تبقى قابلة للاستخدام إلى أن يؤكد FCM أنها غير صالحة بخطأ دائم، أو تتم عملية تنظيف لاحقة معتمدة بعد فترة المراقبة.
11. **لا يتم تفعيل Enforce بناءً على نسبة انتشار تقديرية.** يحتاج قراراً إدارياً وتقريراً يوضح نسب نسخ التطبيق وحالات Unknown وتأثير الحجب المتوقع.
12. **أي تعارض بين تحسين جديد والتوافق الخلفي يُحسم لصالح التوافق الخلفي** إلى أن يُعتمد إنهاء دعم نسخة قديمة بشكل منفصل.

### 3.2 بوابة النشر الخاصة بالتوافق

يُمنع نشر أو تفعيل أي تغيير على Production قبل نجاح التالي:

- اختبار آخر نسخة منشورة حالياً من تطبيق العميل دون تعديلها.
- اختبار نسخة أقدم ما زالت مستخدمة فعلياً، ويُحدد رقمها من بيانات المتجر أو سجلات التطبيق إن توفرت.
- تسجيل الدخول والتسجيل والتحقق واستعادة الجلسة Auto Login.
- إنشاء الطلب ومتابعته وعرض قائمة الطلبات والتفاصيل.
- تسجيل التوكن بالطلب القديم واستقبال إشعار طلب Transactional.
- استقبال حملة عامة وفتح شاشة Inbox وقراءة الإشعار.
- تسجيل الخروج والدخول بحساب آخر على الجهاز نفسه.
- التحقق من Android وiOS كلٌ على حدة.
- مقارنة Request/Response Contract قبل وبعد التعديل للواجهات التي يستخدمها التطبيق.
- تجربة تعطيل كل Feature Flag جديد والتأكد أن المسار القديم يستمر فوراً.

إذا فشل أي سيناريو فلا يتم التفعيل على Production، حتى لو نجحت اختبارات Laravel الداخلية.

## 4. المكونات الحالية وقرار التعامل معها

| المكون الحالي | الاستخدام الحالي | القرار |
|---|---|---|
| `users` | الحساب والتفضيل `is_allow_notify` | المحافظة عليه وإضافة وقت تأكيد التفضيل إذا لزم |
| `devices` | تخزين توكن بحسب المستخدم والمنصة | توسيعه لدعم installation وحالة التوكن والصلاحية والنشاط |
| `notifications` | بيانات الإشعار والجمهور والفلاتر | المحافظة عليه وإضافة الغرض وحالة المعالجة والعدادات اللازمة |
| `users_notifications` | Inbox وحالة sent/failed للمستخدم | المحافظة عليه وفصل أهلية المستخدم عن نتيجة أجهزة المستخدم |
| `notification_tokens` | تسجيل التوكن وsuccess/failed | توسيعه كسجل محاولة إرسال تفصيلي لكل جهاز |
| `NotificationsManger` | اختيار الجمهور وتوجيه الإرسال | تفكيك مسؤولياته داخلياً مع بقاء واجهته الحالية أثناء الانتقال |
| `FCMService` | Topic subscription ثم Topic send | تطويره لاستخدام إرسال مباشر على دفعات مع تصنيف الأخطاء |
| `SendNotificationJob` | معالجة الحملة في وظيفة واحدة | تحويله إلى منسق للحملة وإنشاء وظائف دفعات صغيرة |
| Dashboard Notifications | تعرض `sent_count` باسم تم الوصول | تصحيح المصطلحات وإضافة تقارير الجمهور والأجهزة والأخطاء |

## 5. نموذج البيانات المقترح

### 5.1 توسيع جدول `devices`

تُضاف الحقول بصورة Additive Migration:

| الحقل | النوع المقترح | الغرض |
|---|---|---|
| `installation_id` | string nullable + index غير فريد | معرف ثابت لنسخة التطبيق على الجهاز؛ تُدار فرديته منطقياً مع `withTrashed()` |
| `app_context` | string nullable/default `unknown` | `client`, `driver`, `technical`, `unknown` لتمييز التطبيق دون الاعتماد على دور المستخدم وحده |
| `token_status` | enum/string | `unknown`, `active`, `stale`, `invalid` |
| `notification_permission` | enum/string | `unknown`, `authorized`, `denied`, `not_determined`, `provisional` |
| `permission_checked_at` | timestamp nullable | آخر وقت فحص صلاحية النظام |
| `token_refreshed_at` | timestamp nullable | آخر وقت أكد فيه التطبيق التوكن |
| `last_seen_at` | timestamp nullable | آخر نشاط أرسله التطبيق للسيرفر |
| `app_version` | string nullable | نسخة التطبيق |
| `os_version` | string nullable | إصدار النظام |
| `device_model` | string nullable | موديل الجهاز |
| `invalidated_at` | timestamp nullable | وقت تأكيد بطلان التوكن |
| `invalid_reason` | string nullable | سبب التعطيل الدائم |
| `last_notification_received_at` | timestamp nullable | آخر receipt وصل من التطبيق |
| `last_notification_opened_at` | timestamp nullable | آخر فتح إشعار |

#### قواعد جدول الأجهزة

- لا يبقى القيد المنطقي `user_id + type` هو هوية الجهاز، لأنه يمنع جهازين Android أو جهازين iOS للمستخدم نفسه.
- الهوية الجديدة في الكود هي `installation_id` مع `app_context`، مع بقاء السجلات القديمة قابلة للعمل من دون هذين الحقلين.
- **يُمنع إنشاء `UNIQUE(device_token)` أو `UNIQUE(installation_id)` في Migration الحالية** بسبب وجود `SoftDeletes` ومسار Logout القديم؛ السجل المحذوف ناعماً سيبقى حاجزاً للقيمة في MySQL.
- توضع Indexes غير فريدة للبحث، وتدار الفردية داخل Transaction على مستوى الخدمة باستخدام `withTrashed()` ثم Restore/Update/Rebind بدلاً من Insert أعمى.
- عند وصول توكن موجود مع `installation_id` جديد تُطبق سياسة Merge واضحة لمنع التكرار.
- لا تُحذف التوكنات مباشرة عند أي خطأ عام؛ تتحول إلى `invalid` فقط عند خطأ دائم مؤكد.
- السجلات الحالية تُعامل كسجلات Legacy ولا تُفترض صلاحيتها أو نشاطها.
- جدول `devices` مشترك بين تطبيق العميل والسائق والفني؛ لذلك لا يُشترط `installation_id` أو Device Sync جديد لإرسال الإشعارات التشغيلية إلى السائقين أو الفنيين، وتُعامل أجهزتهم الحالية `legacy/unknown`.

### 5.2 المحافظة على `is_allow_notify`

يُضاف حقل:

```text
is_allow_notify_confirmed_at nullable timestamp
```

ويصبح التفسير:

| الحالة | المعنى |
|---|---|
| `confirmed_at` فارغ | قيمة قديمة أو افتراضية؛ الحالة الحقيقية Unknown |
| `confirmed_at` موجود و`is_allow_notify = 1` | المستخدم سمح صراحة بالحملات التسويقية |
| `confirmed_at` موجود و`is_allow_notify = 0` | المستخدم رفض صراحة الحملات التسويقية |

لا يتم تحويل جميع القيم القديمة إلى Opt-in أو Opt-out بصورة جماعية، لأن البيانات الحالية غير متزامنة مع التطبيق أو الجهاز.

يُضاف API جديد Idempotent يستقبل قيمة Boolean واضحة. يبقى مسار Toggle الحالي كما هو للنسخ القديمة ولا يُزال أو يتغير عقده، إلى أن يثبت من بيانات نسخ التطبيق أنه لم يعد مستخدماً ويصدر قرار مستقل بإنهاء دعمه.

### 5.3 توسيع جدول `notifications`

الحقول المقترحة:

| الحقل | النوع/القيمة الآمنة أولاً | الغرض |
|---|---|---|
| `purpose` | nullable، والقيمة الفارغة = `legacy_unknown` في طبقة التطبيق | `marketing`, `transactional`, `system` بعد التصنيف الصريح |
| `processing_status` | nullable، والقيمة الفارغة = `legacy` في طبقة العرض | `draft`, `queued`, `processing`, `completed`, `partial_failed`, `failed` |
| `started_at` | timestamp nullable | بدء المعالجة |
| `completed_at` | timestamp nullable | انتهاء المعالجة |
| `targeted_users_count` | unsigned integer default `0` | الجمهور قبل فحص الأجهزة |
| `eligible_users_count` | unsigned integer default `0` | المستخدمون المؤهلون بعد قواعد السماح |
| `eligible_devices_count` | unsigned integer default `0` | الأجهزة المؤهلة فعلياً |
| `accepted_by_fcm_count` | unsigned integer default `0` | طلبات قبلها FCM |
| `permanent_failed_count` | unsigned integer default `0` | أخطاء دائمة |
| `transient_failed_count` | unsigned integer default `0` | أخطاء مؤقتة بعد استنفاد المحاولات |
| `received_count` | unsigned integer default `0` | receipts من التطبيق حيث يمكن قياسها |
| `opened_count` | unsigned integer default `0` | مرات فتح الإشعار |

العدادات Snapshot لتسريع لوحة التحكم، ومصدر الحقيقة التفصيلي يبقى سجلات المستخدمين والأجهزة.

جميع الحقول الجديدة Nullable أو لها Default آمن لا يغيّر السلوك. **لا يوضع `purpose = marketing` كقيمة افتراضية في قاعدة البيانات** لأن إشعارات الطلب والسائقين والفنيين قد تُنشأ من Observers وJobs قديمة دون إرسال هذا الحقل، وتصنيفها كتسويق سيؤدي إلى حجبها خطأً.

يتم الانتقال إلى التصنيف الصريح تدريجياً:

- `OrderRepresentativeObserver` وإشعارات حالة الطلب: `transactional`.
- التنبيهات التقنية أو الداخلية: `system`.
- الترحيب والسلة المتروكة والميلاد وعدم النشاط والحملات اليدوية: `marketing` ما لم يثبت من منطق العمل خلاف ذلك.
- أي منشئ قديم لم يُحدّث بعد يبقى `legacy_unknown` ويستمر بالمسار الحالي دون حجب.
- يجري جرد واختبار `WelcomeNotificationJob`, `AbandonedCartJob`, `CelebrateBirthdayJob`, `InactiveAfterOrderJob`, `OrderRepresentativeObserver`, و`CoverageNotificationService` وكل موضع `Notification::create()` قبل تفعيل Enforcement.

### 5.4 توسيع `users_notifications`

يبقى سجل واحد لكل مستخدم في الحملة. تُضاف حقول توضح الأهلية دون كسر `status` الحالي:

| الحقل | الغرض |
|---|---|
| `eligibility_status` | `eligible`, `no_device`, `inactive`, `marketing_disabled`, `permission_denied`, `no_valid_token` |
| `eligibility_reason` | سبب مختصر قابل للتقرير |
| `accepted_devices_count` | عدد أجهزة المستخدم التي قبلها FCM |
| `failed_devices_count` | عدد الأجهزة الفاشلة |

يبقى `read_at` خاصاً بصندوق الإشعارات داخل التطبيق، ولا يفسر كفتح Push.

#### قيد الـPolymorphic Relation — Binding

جدول `users_notifications` مشترك بين `Notification` و`BannerNotification`. لذلك:

- كل Query أو Update أو Aggregate خاص بحملات الإشعارات يجب أن يضيف شرط `notifications_type = Notification::class`، وليس `notifications_id` وحده.
- يفضل استخدام علاقة Eloquent المورفية المعرفة في المشروع؛ وإذا استُخدم Query Builder فيجب كتابة شرط النوع صراحة.
- يمنع أي تحديث جماعي قد يلمس `next_vision_date` أو حالات ظهور البنرات.
- تضاف Regression Tests تثبت أن إنشاء الحملة وإرسالها وإعادة المحاولة لا يغير سجلات `BannerNotification` حتى لو تشابهت المعرفات الرقمية.

### 5.5 توسيع `notification_tokens`

بدلاً من إنشاء `notification_deliveries` جديد، يُوسع الجدول الحالي:

| الحقل | الغرض |
|---|---|
| `user_id` | المستخدم وقت الإرسال |
| `device_id` | الجهاز المستهدف |
| `installation_id` | Snapshot لتعقب التثبيت |
| `platform` | iOS أو Android أو Huawei |
| `status` | `queued`, `accepted`, `transient_failed`, `permanent_failed`, `received`, `opened` |
| `fcm_message_id` | معرف FCM عند توفره |
| `error_code` | كود الخطأ المنظم |
| `error_message` | رسالة مختصرة بعد إزالة البيانات الحساسة |
| `attempts` | عدد المحاولات |
| `queued_at` | وقت الانتظار |
| `accepted_at` | وقت قبول FCM |
| `failed_at` | وقت الفشل النهائي |
| `received_at` | receipt من التطبيق |
| `opened_at` | فتح الإشعار |

القيم القديمة `success` و`failed` تبقى قابلة للقراءة كتاريخ Legacy، وتُحول في طبقة العرض إلى المصطلحات الصحيحة.

## 6. قواعد اختيار الجمهور والأجهزة

### 6.1 المرحلة الأولى اختيار الجمهور

تُحافظ كل فلاتر النظام الحالية:

- `for = all` أو `users`.
- التسجيل من وإلى.
- تاريخ الطلبات.
- الحد الأدنى والأقصى لعدد الطلبات.
- المستخدمون المحددون.
- القنوات `apps`, WhatsApp وغيرها.

ثم تضاف قواعد واضحة بحسب الغرض.

### 6.2 الحملات التسويقية

الجمهور المستهدف مبدئياً:

- المستخدم غير محذوف.
- يحمل دور `client`.
- `is_active = 1` عند اعتماد الإدارة لهذا الشرط.
- يطابق فلاتر الحملة الحالية.

أهلية Push على مستوى المستخدم والجهاز:

- يوجد جهاز غير محذوف.
- التوكن موجود وغير `invalid`.
- صلاحية الجهاز ليست `denied`.
- التفضيل التسويقي ليس رفضاً صريحاً مؤكداً.

خلال الفترة الانتقالية:

- `notification_permission = unknown` يمكن الإرسال إليه في وضع Observation.
- قيمة `is_allow_notify` القديمة دون `confirmed_at` تعامل `unknown` ولا تُفسر كرفض صريح.
- بعد انتشار نسخة Flutter الجديدة تتحول القواعد تدريجياً إلى Enforcement.

### 6.3 الإشعارات التشغيلية

مثل حالة الطلب ووصول السائق:

- لا تعتمد على التفضيل التسويقي.
- تعتمد على وجود جهاز وتوكن غير invalid وصلاحية ليست denied.
- تبقى سجلات Inbox داخل التطبيق حتى لو تعذر Push.
- تشمل تطبيق العميل والسائق والفني، ولا يجوز قصر اختيار الأجهزة على دور `client` في هذا المسار.
- جهاز السائق أو الفني القديم الذي لا يملك `installation_id`, `app_context` أو permission يبقى مؤهلاً كـ`legacy/unknown` في وضع Observe.
- يستمر `OrderRepresentativeObserver` والمسارات التشغيلية الحالية في العمل حتى قبل إصدار تحديثات تطبيقات السائقين والفنيين.

### 6.4 تعدد الأجهزة

- الإرسال يكون إلى جميع الأجهزة المؤهلة للمستخدم، وليس `MAX(id)` فقط.
- تعرض لوحة التحكم عدد المستخدمين وعدد الأجهزة كلٌ على حدة.
- تزال التوكنات المكررة قبل تجهيز دفعات الإرسال.
- يمنع إرسال التوكن نفسه مرتين في الحملة نفسها بقيد Idempotency.

## 7. مسار الإرسال الجديد مع المحافظة على الخدمات الحالية

```text
إنشاء Notification
→ اختيار الجمهور الحالي
→ حفظ users_notifications على دفعات
→ تقييم أهلية كل مستخدم وأجهزته
→ حفظ notification_tokens بالحالة queued
→ تقسيم الأجهزة إلى دفعات
→ إرسال كل دفعة في Job مستقلة
→ تصنيف نتائج FCM لكل توكن
→ تحديث حالة الجهاز عند الخطأ الدائم
→ تجميع نتائج المستخدم والحملة
→ عرض التقرير في لوحة التحكم
```

### 7.1 الـQueue

- يبقى `SendNotificationJob` كنقطة بدء ومنسق للحملة.
- لا ينفذ جميع الاتصالات داخل Job واحدة.
- يبدأ بحجم قابل للضبط بين **50 و100 جهاز لكل Job** مع القيمة الأولية `50`، ولا يُرفع إلا بعد قياس زمن p95 على Staging وProduction.
- إذا استُخدم HTTP v1 بطلب مستقل لكل رسالة، تُستخدم Concurrency محدودة ومضبوطة مثل `Http::pool()` بحد آمن، وليس 500 طلب تسلسلي أو تزامن غير محدود.
- تستخدم `chunkById` أو Cursor بدلاً من تحميل آلاف Models في الذاكرة.
- كل وظيفة دفعة Idempotent ويمكن إعادة محاولتها دون تكرار الإرسال المقبول سابقاً.
- قبل إرسال كل توكن يعاد فحص سجل المحاولة؛ الحالات `accepted`, `received`, `opened` لا تُرسل مرة أخرى.
- تُنسق قيم `job timeout`, `worker --timeout` و`retry_after` معاً، ويجب أن يكون Timeout العامل أقل من `retry_after` بهامش أمان واضح. مع القيمة الحالية `retry_after = 90` يجب ألا تقترب الوظيفة من 90 ثانية.
- إذا أثبت القياس الحاجة إلى وقت أطول، يعدل `retry_after` والـWorker Supervisor معاً في نافذة نشر موثقة؛ لا يعدل أحدهما منفرداً.
- تبقى Database Queue في هذه المرحلة؛ لا يُفرض Redis أو Horizon كشرط لنجاح الخطة.
- تضاف صفحة أو مؤشرات لحالة الدفعات والأخطاء، مع إمكانية إعادة محاولة الأخطاء المؤقتة فقط.

### 7.2 FCM

- يُطور `FCMService` الحالي بدلاً من إنشاء خدمة موازية.
- يُوقف الاعتماد على IID Topic subscription كوسيلة لقياس وصول المستخدمين.
- في المرحلة الأولى يُراعى الاعتماد الحالي على `google/apiclient`. يستخدم HTTP v1 مع OAuth الحالي وإرسال مباشر محدود التزامن، أو تُعتمد إضافة Firebase Admin SDK كقرار Dependency منفصل بعد اختبارها؛ لا تفترض الخطة وجود `kreait/laravel-firebase` حالياً.
- `accepted` تعني أن FCM قبل الرسالة فقط.
- لا تتحول إلى `received` أو `opened` إلا عند وصول أحداث من تطبيق Flutter في المرحلة التالية.

### 7.3 تصنيف الأخطاء

| النوع | أمثلة | الإجراء |
|---|---|---|
| دائم | `UNREGISTERED`, token not registered, token malformed المؤكد | `devices.token_status = invalid` وإيقاف استخدام التوكن |
| إعدادات | Sender mismatch, APNs credentials | إيقاف الدفعة وتنبيه الإدارة؛ لا حذف للتوكنات جماعياً |
| مؤقت | Timeout, 5xx, unavailable, rate limit | إعادة محاولة مع Backoff |
| Payload | حجم أو مفاتيح غير صالحة | فشل الحملة أو الدفعة مع تقرير واضح؛ لا اتهام التوكن |

يُلغى `forceDelete` العام للتوكنات الفاشلة. يستخدم Soft Delete أو Status مع سبب وتاريخ، ولا يتم الحذف النهائي إلا بأداة صيانة معتمدة.

### 7.4 تنبيهات Telegram

- لا تُرسل رسالة Telegram لكل توكن أو Batch Job.
- يرسل تقرير واحد مجمع عند انتهاء الحملة يتضمن الأعداد النهائية والأخطاء المختصرة.
- ترسل رسالة فورية فقط للأخطاء الحرجة مثل فشل Credentials أو APNs أو توقف الحملة بالكامل.
- تغيير `is_allow_notify` من المستخدم يمكن أن يبقى وفق السلوك الحالي، مع Rate Limit ومنع التكرار إذا تبين أنه يسبب ضوضاء.
- نجاح أو فشل توكن فردي يظهر في لوحة الحملة والسجلات، وليس في قناة الدعم.

## 8. إصلاحات التوافق الحالية

### 8.1 خطأ `explode()`

- لا يُضاف Eloquent Cast افتراضي من نوع `array` إلى `for_data`، لأن الحقل يخزن JSON لبعض إشعارات التطبيقات وCSV String للهواتف والبريد وWhatsApp.
- إنشاء Normalizer/Parser صريح يُستدعى في مواضع اختيار الجمهور، ويفهم `null`, Array, JSON Array, scalar وCSV String باستخدام فحص JSON آمن مثل النمط الموجود في `ToolHelper::isJson()`.
- لا يغير Accessor القيمة الأصلية التي تعتمد عليها القنوات القديمة؛ يمكن توفير قيمة محسوبة مثل `normalized_for_data` أو Service مستقلة.
- يمنع استدعاء `explode()` قبل التأكد أن القيمة String، ولا يطبق CSV parsing على JSON.
- Migration `2026_09_23_103222_change_for_data_column_type_in_notifications_table.php` حولت العمود إلى `longText` بالفعل؛ **لا تُنشأ Migration جديدة لتغيير نوع العمود**. يكتفى بالتحقق من أنها مطبقة على Production.
- تضاف اختبارات منفصلة لـApps JSON/Array، أرقام الهواتف CSV، عناوين البريد CSV، WhatsApp، القيمة المفردة والقيمة الفارغة.

### 8.2 المصطلحات

تغيير واجهة لوحة التحكم:

| المصطلح الحالي | المصطلح الجديد |
|---|---|
| تم الوصول / Delivered | قُبل من FCM |
| فشل الإرسال بسبب عدم وجود توكن | غير مؤهل لا يوجد جهاز مسجل |
| إجمالي المستهدفين | الجمهور المستهدف |
| Sent | Accepted by FCM في التقارير الجديدة |

تبقى القيم القديمة في قاعدة البيانات للتوافق، وتُترجم في طبقة العرض.

## 10. عقود Backend اللازمة لمرحلة Flutter التالية

تُجهز في Laravel الآن، ويستخدمها تطبيق Flutter لاحقاً.

### 10.1 مزامنة الجهاز

```http
POST /api/devices/sync
```

مدخلات أساسية:

```json
{
  "installation_id": "uuid",
  "device_token": "fcm-token",
  "platform": "ios",
  "app_context": "client",
  "notification_permission": "authorized",
  "app_version": "4.2.0",
  "os_version": "18.0",
  "device_model": "iPhone"
}
```

خصائصه:

- Idempotent بحسب `installation_id`.
- يعمل لأي مستخدم مصادق عليه عبر Guard المشروع المناسب، وليس للعملاء فقط، ليخدم تطبيقات العميل والسائق والفني مستقبلاً.
- يربط الجهاز بالمستخدم المصادق عليه، ويستخدم `app_context` المرسل من التطبيق ولا يستنتجه من Role وحده لأن المستخدم قد يحمل أكثر من دور.
- يدمج السجلات المتعارضة بالتوكن بصورة آمنة.
- يبحث باستخدام `withTrashed()` ويستعيد أو يعيد ربط السجل بدلاً من الاصطدام بسجل محذوف ناعماً.
- يحدث `last_seen_at` و`token_refreshed_at` حسب البيانات المرسلة.
- لا يعرض توكنات أو بيانات مستخدمين آخرين.
- عدم استخدام التطبيقات القديمة لهذا المسار لا يمنع تسجيل التوكن أو استقبال الإشعارات.

### 10.2 فصل الجهاز عند Logout

```http
DELETE /api/devices/{installation_id}/user
```

يفصل `user_id` عن الجهاز بعد التحقق من الملكية، ولا يحذف تثبيت التطبيق أو التوكن دون داعٍ.

### 10.3 تحديث التفضيل التسويقي

```http
PUT /api/client/notification-preference
```

```json
{
  "marketing_push_enabled": true
}
```

يحدث `is_allow_notify` و`is_allow_notify_confirmed_at` بقيمة صريحة، ولا يستخدم Toggle قابل للانقلاب عند إعادة الطلب.

### 10.4 تسجيل أحداث الإشعار

```http
POST /api/client/notifications/events
```

يقبل حدثاً Idempotent مرتبطاً بـ`notification_id`, `device_id` أو `installation_id`, و`event_type` مثل received أو opened. يمنع تسجيل الحدث مرتين بمفتاح حدث فريد.

## 11. ترحيل البيانات الحالية

1. لا تُحذف أي أجهزة أو توكنات حالية أثناء Migration.
2. كل سجل جهاز موجود يحصل على:
   - `token_status = unknown`.
   - `notification_permission = unknown`.
   - `installation_id = null` أو معرف Legacy داخلي غير معتمد من التطبيق.
   - `last_seen_at = null`.
3. قيم `is_allow_notify` الحالية تبقى كما هي، لكن `confirmed_at = null` لجميع السجلات القديمة.
4. حالات `notification_tokens.success` القديمة تعرض كـLegacy Accepted، وليس Delivered.
5. عند أول Device Sync من Flutter، يُبحث عن السجل بالتوكن والمستخدم والمنصة ويُدمج قبل إنشاء سجل جديد.
6. لا يتم تنظيف Legacy tokens إلا بعد فترة مراقبة 60 إلى 90 يوماً ووفق تقرير واضح.

## 12. Feature Flags وخطة الانتقال

الخيارات المقترحة:

```text
notifications.device_sync_enabled
notifications.direct_fcm_enabled
notifications.permission_mode = observe|enforce
notifications.marketing_preference_mode = observe|enforce
notifications.delivery_events_enabled
notifications.new_dashboard_metrics_enabled
```

كل Feature Flag جديد يبدأ بقيمة `false` في Production، باستثناء أوضاع المراقبة التي لا تغير السلوك. المسار Legacy لا يوضع خلف خيار يمكن تعطيله بالخطأ خلال هذه المرحلة.

### الترتيب

1. تثبيت نسخة من عقود APIs وFCM Payloads الحالية كـContract Fixtures قبل التعديل.
2. نشر Additive Migrations فقط دون تغيير أي Query أو سلوك إرسال.
3. نشر كود Laravel الجديد وجميع Feature Flags المؤثرة مغلقة.
4. تشغيل Device Sync APIs الجديدة دون اعتماد Flutter عليها ودون المساس بمسار تسجيل التوكن القديم.
5. تشغيل القياسات الجديدة في وضع Observe؛ قيم Unknown لا تمنع الإرسال.
6. تشغيل لوحة التحكم الجديدة وقراءة البيانات بالتوازي دون تغيير مسار الحملات.
7. مقارنة نتائج المسار القديم والجديد في Shadow/Simulation دون إرسال مزدوج للمستخدم.
8. تجربة الإرسال المباشر على حسابات الفريق ثم عينة صغيرة معتمدة.
9. رفع النسبة تدريجياً مع إمكانية الرجوع الفوري بالـFeature Flag.
10. اعتماد المسار الجديد للحملات الجماعية بعد نجاح المقارنة واختبارات النسخ القديمة.
11. نشر Flutter في مرحلة مستقلة؛ المستخدم القديم يستمر على المسار Legacy.
12. لا يتحول permission أو marketing preference إلى Enforce إلا بعد بيانات انتشار كافية واعتماد منفصل.

### الرجوع الآمن

- الرجوع الأساسي يكون بإغلاق Feature Flags الجديدة، وليس بإرجاع Migration أو حذف بيانات.
- تبقى الأعمدة والجداول المضافة غير مؤثرة عند إغلاق الخصائص.
- لا يتم عمل Down Migration على Production كإجراء طوارئ إلا بخطة مستقلة وبعد نسخة احتياطية.
- عند مشكلة في Direct FCM يعود الإرسال للمسار الحالي، مع منع الإرسال المزدوج عبر مفتاح Idempotency للحملة والجهاز.
- أي دفعة قُبلت بالفعل من FCM لا يعاد إرسالها عند الرجوع أو إعادة المحاولة.

## 13. الاختبارات المطلوبة

### 13.1 اختبارات قاعدة البيانات والنماذج

- Migration up/down آمنة.
- السجلات القديمة تبقى قابلة للقراءة.
- لا توجد Unique Constraints تتعارض مع SoftDeletes؛ يجري اختبار Merge/Restore/Rebind للتوكن وinstallation باستخدام `withTrashed()`.
- أكثر من جهاز من المنصة نفسها للمستخدم.
- جميع الحقول الجديدة تقبل إنشاء `Notification` و`Device` من الكود القديم دون تمريرها.
- `purpose = null` يعامل `legacy_unknown` ولا يتحول تلقائياً إلى Marketing.

### 13.2 اختبارات الجمهور

- `all` لا يشمل المحذوفين.
- الحملات التسويقية تستهدف client فقط.
- فلاتر التسجيل والطلبات الحالية لا تتغير.
- الرفض الصريح المؤكد يمنع Marketing فقط.
- Transactional لا يعتمد على Marketing preference.
- Permission denied يمنع Push ولا يمنع Inbox.
- Unknown يعمل حسب Observe أو Enforce.
- إشعارات السائق والفني التشغيلية تستمر لأجهزة Legacy التي لا تملك `installation_id` أو permission.

### 13.3 اختبارات الإرسال

- 14 ألف مستخدم لا يُعالجون داخل Job واحدة.
- تقسيم الأجهزة إلى دفعات 50 افتراضياً وقابلة للضبط ضمن 50–100 بناءً على القياس.
- إعادة المحاولة لا تكرر إرسال accepted سابقاً.
- الخطأ الدائم يعطل التوكن الصحيح فقط.
- الخطأ المؤقت لا يحذف التوكن.
- خطأ credentials لا يعطل جميع التوكنات.
- تعدد الأجهزة يُسجل لكل جهاز ويجمع لكل مستخدم.
- زمن p95 للـJob يبقى تحت `retry_after` بهامش أمان، واختبار بطء Google لا يؤدي إلى عاملين يرسلان الدفعة نفسها.
- Concurrency محدودة ولا تسبب Rate Limit أو استهلاك اتصالات غير منضبط.

### 13.4 اختبارات التقارير

- عدادات الحملة تساوي سجلات التفاصيل.
- `accepted_by_fcm` لا يظهر باسم Delivered.
- No Device يظهر كعدم أهلية وليس خطأ FCM.
- التصدير لا يحتوي التوكن الخام أو بيانات حساسة غير لازمة.

### 13.5 Regression

- إشعارات الطلب الفردية الحالية.
- Inbox و`read_at`.
- WhatsApp والقنوات غير Apps.
- الإرسال الفوري والمجدول.
- اختيار مستخدمين محددين.
- صلاحيات لوحة التحكم.
- Jobs وObservers الحالية: الترحيب، السلة المتروكة، الميلاد، عدم النشاط، إشعارات الطلب والسائق وCoverage.
- `users_notifications` المورفي: لا تتغير سجلات `BannerNotification` أو `next_vision_date` أثناء إرسال حملة أو Retry.
- `for_data` بصيغ Apps JSON/Array وPhone/Email/WhatsApp CSV.
- Telegram: تقرير مجمع واحد للحملة، ولا توجد رسالة لكل دفعة أو توكن.

### 13.6 اختبارات توافق نسخ التطبيق القديمة

- Contract Tests للمسارات الحالية باستخدام Request/Response Fixtures مأخوذة قبل التعديل.
- قبول طلب تسجيل التوكن القديم من دون `installation_id` أو permission أو app version.
- التأكد أن إضافة حقول Response لا تغير الحقول الحالية أو أنواعها أو Nullability المتوقعة.
- تثبيت FCM Payload القديم واختبار أن مفاتيحه وقيمه الأساسية لم تتغير.
- Smoke Test فعلي بآخر نسخة منشورة ونسخة أقدم على Android.
- Smoke Test فعلي بآخر نسخة منشورة ونسخة أقدم على iOS.
- اختبار Auto Login لمستخدم لم يحدّث التطبيق ولم ينفذ Device Sync الجديد.
- اختبار مستخدم قديم قيمته `permission = unknown` والتأكد أنه لا يُحجب في Observe.
- اختبار إغلاق Feature Flags أثناء التشغيل والتأكد أن المسار Legacy يعود دون خطأ أو تكرار.
- حفظ أرقام النسخ والأجهزة ونتيجة كل سيناريو في تقرير Staging موقع قبل Production.

## 14. معايير القبول

يُعتبر نطاق Laravel ولوحة التحكم مكتملاً عندما:

1. لا تسمى نتيجة FCM Topic أو HTTP success باسم Delivered.
2. تعرض الحملة الجمهور والمستخدمين المؤهلين والأجهزة بصورة منفصلة.
3. يستطيع النظام دعم عدة أجهزة للمستخدم.
4. لا يعتمد تسجيل التوكن على `user_id + platform` فقط.
5. لا تُحذف التوكنات بسبب أخطاء مؤقتة أو أخطاء إعدادات.
6. لا تتجاوز الحملة الكبيرة Timeout لأنها مقسمة إلى Jobs صغيرة.
7. لا يفشل `for_data` إذا وصل Array أو JSON أو String قديم.
8. توجد API آمنة وIdempotent لمزامنة الجهاز وفصله وتحديث التفضيل.
9. تبقى الإشعارات الحالية وWhatsApp وInbox تعمل دون تغيير غير مقصود.
10. تعرض لوحة الصحة حالات الجهاز والتوكن والتفضيل والصلاحية والنشاط.
11. توجد اختبارات آلية وتقرير Staging قبل Production.
12. لا يتم تفعيل Enforcement حتى تصبح نسخة Flutter الداعمة منتشرة وتوجد بيانات كافية.
13. تعمل آخر نسخة منشورة ونسخة أقدم مستخدمة فعلياً دون تحديث إجباري.
14. تقبل APIs الحالية الطلبات القديمة وتعيد الحقول الحالية بالأسماء والأنواع نفسها.
15. يستمر تسجيل التوكن Legacy واستقبال الإشعارات عند عدم وجود `installation_id` أو permission أو app version.
16. يمكن تعطيل جميع التحسينات المؤثرة والعودة للمسار الحالي دون Rollback لقاعدة البيانات.
17. لا يُنشر التغيير إذا لم ينجح تقرير بوابة التوافق على Android وiOS.
18. تستمر إشعارات السائقين والفنيين والـObservers والـCron Jobs الحالية دون اشتراط Device Sync جديد.
19. لا يوجد Unique Constraint على `device_token` أو `installation_id` يتعارض مع SoftDeletes، وتنجح دورة Logout ثم Login بالحساب نفسه أو حساب آخر.
20. لا تنشأ Migration مكررة لـ`for_data`، ولا يستخدم الحقل Eloquent Array Cast يكسر CSV.
21. كل استعلام خاص بـ`users_notifications` يقيد `notifications_type` وتحمي الاختبارات سجلات البنرات.
22. لا ينتج عن Queue Timeout إرسال مكرر، ولا ترسل Telegram رسالة لكل Batch.
